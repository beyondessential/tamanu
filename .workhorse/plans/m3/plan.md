# M3 · Server error on admitted encounter page

## What the toast actually proves

The toast body is built in `packages/web/app/api/TamanuApi.jsx` (`buildErrorToast`), and
the "Message:" line is `error.title`. The string `Server error` is only ever produced in
one place: `readResponse` in `packages/errors/src/extractErrorFromFetchResponse.ts`. It
appears on exactly four branches, all client-side, all reached only when the response is
**not** ok:

- the body is empty (`No response data`)
- the body can't be decoded as text (`Invalid text encoding in response`)
- the body isn't valid JSON (`Invalid JSON in response`)
- the body is JSON but has neither a `type` (RFC 9457) nor an `error` key (`Unknown response format`)

Every error either Tamanu server raises goes through `errorHandlerProblem`
(`packages/shared/src/utils/errorHandlerProblem.js`), which always sends
`problem.toJSON()` — and that always carries a `type`. So a response from a Tamanu error
handler can never produce this toast.

Concretely, for `suggestions/practitioner/:id`:

- a DB failure would read `Message: Database`
- any other unhandled exception would read `Message: <ErrorName>`
- an unknown practitioner id raises `NotFoundError`, typed `not-found`, which
  `classifyApiError` deliberately keeps **silent** — no toast at all
- a permission failure is `forbidden`, also silent
- rate limiting is `rate-limited`, also silent

So the failing response did not come from the facility server's error handler. The
suggester code itself is not implicated: `git diff release/2.61..release/2.62` on
`packages/shared/src/services/suggestions/suggestions.js` is empty, and the lookup route
is a plain `findOne` by primary key with no filters.

## What can produce a bodyless non-2xx

1. **The servers' catch-all 404.** `packages/facility-server/app/createApiApp.js:128`,
   `packages/facility-server/app/createSyncApp.js:42` and
   `packages/central-server/app/createApi.js:153` all answer unmatched paths with
   `res.status(404).end()` — a 404 with a zero-length body. Anything that lands there
   surfaces to the user as "Something went wrong on the server" instead of a silent
   not-found. This is a real defect regardless of whether it caused this report.
2. **The reverse proxy in front of the facility server.** An empty-bodied 502/504 (the
   upstream died, was restarting, or dropped the connection) lands on the same
   `No response data` branch; an HTML error page lands on `Invalid JSON in response`.

For the reported path the route does match (`/practitioner/:id` is registered and the id
in the screenshot is a well-formed UUID), which points at (2).

## Next step to close it out

Pull the facility server log for that CD deployment around the time of the screenshot.
`errorHandlerProblem` logs `Error <status> (<type>)` for every error it handles. If there
is **no** log line for `suggestions/practitioner/cad341b9-…`, the request never reached
the app and the response was generated by the proxy — most likely because the process was
down or restarting (2.62 carries `fix(sync): batch changelog insertion, avoiding OOM
during persist phase` (#10703), and an OOM kill mid-request produces exactly this shape).

## Hardening worth doing either way

- [ ] Replace the three `res.status(404).end()` catch-alls with a `NotFoundError` raised
      through the normal error handler, so an unmatched path is typed `not-found` and stays
      silent instead of raising a server-error toast.
- [ ] Guard `Suggester.fetchCurrentOption` (`packages/ui-components/src/components/Suggester/Suggester.js`)
      against an empty value: `fetchCurrentOption('')` requests `suggestions/<endpoint>/`,
      which falls through to the list route rather than the lookup and returns an array to a
      single-option formatter.
