Released 17-08-2026

Tamanu v2.62 moves a large slice of server configuration into the admin panel, so administrators manage it themselves instead of editing files on the server. Medications gain a send-to-pharmacy workflow at discharge and at prescribing, and lab requests gain out-of-range result flags, edited-entry markers and configurable priority handling.

---

# 🌟 Major Features and Changes

## Tamanu Desktop

### _Send to Pharmacy from Discharge and Prescribing_

The send-to-pharmacy workflow now reaches the two points where prescribing actually happens: writing a new prescription, and discharging a patient. Rather than prescribing first and sending to pharmacy as a separate step, a clinician can do both in one action, with stock and previous requests visible while deciding. At discharge, the medications going home with the patient default to being sent, so nothing is missed on the way out the door.

**Key features**

- **Send to pharmacy at discharge** - The discharge modal lists the patient's medications with a send-to-pharmacy column, ticked by default for encounter medications and unticked for other ongoing medications.
- **Send to pharmacy when prescribing** - A send-to-pharmacy option on the new prescription modal, off by default, with the prescription type shown once it is selected.
- **Dispensing quantity required** - 'Discharge qty' becomes 'Dispensing qty' and must be filled in, so pharmacy receives a quantity it can act on.
- **Ordering prescriber recorded** - Set to the current user and required whenever medications are being sent.
- **Stock and request history in view** - Columns show whether each medication is in stock, when a request was last sent, and whether that request is still active or already dispensed.
- **Visible only where pharmacy ordering is in use** - The pharmacy fields appear only for deployments with the pharmacy order setting enabled.

### _Lab Request Priority and Result Flags_

Clinicians reviewing an individual lab request now see the same result highlighting that the patient-level results table already provided, so an abnormal result is visible at the point of review rather than only after navigating to the patient's lab results tab. Priority handling also becomes configurable, so a deployment can require a priority on every request and control whether it can be changed afterwards.

**Key features**

- **Out-of-range results flagged in the request view** - Numeric results outside their reference range are highlighted in an individual lab request, with a tooltip naming the bound that was breached.
- **Flagged as soon as results are entered** - Highlighting does not wait on the request's status.
- **Edited-entry markers** - Result, method, lab officer, verification and completed date each carry a faded asterisk once changed after first entry, with an "* Edited entry" note below the table.
- **Range and flag always agree** - The reference range shown and the highlight are derived from the same calculation, including sex-based ranges.
- **Optional mandatory priority** - A deployment can require a priority to be chosen when a lab request is created.
- **Optional priority lock** - A deployment can stop priority being edited once a request has been submitted.

## System Administration

### _Configuration Managed in the Admin Panel_

A large amount of configuration that previously lived in files on each server is now database-backed settings that administrators edit in the admin panel. Mail, scheduled tasks, integrations, localisation, reporting and rate limiting can be changed without server access, with validation on entry and per-facility overrides where they make sense. Existing values are carried across automatically during the upgrade, so nothing needs re-entering and behaviour does not change.

**Key features**

- **Editable without server access** - Values that previously required a file edit and a deployment are now managed in the admin panel.
- **Carried across on upgrade** - Existing configuration is migrated into settings automatically. A value already set in settings always wins, so nothing an operator has configured is overwritten.
- **Applied without a restart** - A saved setting takes effect on the next read, and the few that genuinely need a restart are marked in the editor.
- **Searchable** - Settings can be found by name, path or description, with the closest matches ranked first.
- **High-risk settings protected** - Changing a setting marked high risk now requires full administrative permission, enforced by the server rather than only hidden in the interface.
- **Per-facility overrides** - A facility can override individual values and inherit the rest.
- **Integration credentials encrypted and distributed automatically** - Secrets such as integration passwords and API tokens are encrypted with one deployment-wide key, which central generates and each facility receives over its authenticated sync connection. Placing a key on each server by hand is no longer required.

# 🔧 System Enhancements

### _Vitals and Charting Time Ranges_

Vitals and charting graphs gain last 7 days, last 30 days and last year ranges, at the encounter level and for program registry charts, so a clinician can look at a longer trend without exporting the data.

---

### _Sync Lookup Self-Healing_

The central server's sync lookup table now repairs itself when source data changes without advancing the sync clock, which is what happens during a migration or a bulk data change. Affected rows are rebuilt without moving their sync tick, so facilities are not made to re-download records they already hold, and an upgrade will not complete while the table is still inconsistent. This reduces the risk of sync drift after an upgrade.

---

### _Hard Deletes Captured in the Audit Changelog_

A permanently removed row is now recorded in the changelog, capturing the record as it stood immediately before removal and marking it as a hard delete, so a permanent deletion is no longer invisible in audit history. Changelog writing and its attachment to sync were also made materially more memory-efficient, which reduces sync failures on large deployments.

# 🐛 Tweaks and Bug Fixes

## Desktop

- **Invoicing** - Details and Ordered by are now required on every invoice line, so clearing Details no longer silently deletes the line; lines are removed through the explicit Delete action. The reason for a discount or mark-up is now visible on the item row, and a stale sliding fee discount no longer survives a change of family size.
- **Medications** - The View patient link opens the patient summary, the dispensed medication popup shows the medication actually dispensed, and the dispense modal loads its list correctly on first open. 'Discontinued by' defaults to the current user.
- **Charts** - Chart edit-history timestamps display in local time rather than UTC.
- **Scheduling** - A booking running past midnight now shows a date on both ends of its time range, so a multi-day stay reads the same on every day it covers.
- **Patient documents** - Double-clicking Add no longer creates duplicate documents.
- **Admin panel** - Corrections to the view-defaults modal layout and to several report and settings editor issues.
- **General** - Validation errors no longer leave a white gap in dialogs.

## Mobile

- **Dates** - Dates before 1970 can now be entered.
- **Vaccines** - The administered vaccine table now refreshes after an edit.
- **Performance** - Program form lists load faster.
- **Sync** - Sync session errors are reported to central.

## System

- **Sync** - An unreachable sync process is now reported as such instead of a generic fetch failure, and facilities record their sync credentials without needing central to be reachable.
- **Reports** - Central refuses report writes when reporting schemas fail to initialise, rather than writing into a broken schema.
- **FHIR** - Survey response encounters are materialised.

# ⚠️ Critical Upgrade Notes

### Required

**_Configuration moved into settings_**

- Existing configuration migrates into settings automatically during the upgrade, so no values need re-entering. Review the settings in the admin panel afterwards to confirm they came across as expected.
- Changing a setting marked high risk now requires full administrative permission. Confirm the right people hold it before they need it.
- Configuration files are still read as a fallback for anything not yet migrated, so do not remove them as part of this upgrade.
- Two new environment variables are available, `PROXY_TRUSTED` and `DISK_PATH`, both with defaults. Set them only if your deployment needs values other than the defaults.

**_Sync lookup rebuild_**

- The central upgrade now performs a full sync lookup rebuild as its final step and will not complete while the table is inconsistent. Allow extra time in the upgrade window for large databases.

### Optional

**_Send to pharmacy_**

- The pharmacy fields at discharge and prescribing appear only where the pharmacy order setting is enabled. Decide whether your deployment adopts this workflow.

**_Lab request priority_**

- Two settings control priority handling, `features.labRequest.priorityMandatory` and `features.labRequest.priorityEditable`. Both ship with defaults that preserve current behaviour, so change them only if you want priority to be required, or to be locked after submission.

**_Lab result flags_**

- Out-of-range highlighting relies on reference ranges configured against lab test types. Tests with no range configured are simply not flagged, so populate ranges where you want the flags to appear.

## Upgrade Steps and Recommended Testing

### Required

**_Configuration moved into settings_**

- After upgrading, spot-check migrated settings in the admin panel against your previous configuration, particularly mail, integrations and scheduled tasks.
- Confirm an administrator without full permission cannot change a high-risk setting, and that one with it can.
- On a multi-facility deployment, confirm facilities can decrypt integration credentials after their first sync.

**_Sync lookup rebuild_**

- Run the upgrade against a copy of a production-sized database first and record how long the rebuild step takes.
- Confirm facilities do not re-pull large volumes of unchanged records after the upgrade.

### Optional

**_Send to pharmacy_**

- Discharge a patient with both encounter and ongoing medications, and confirm the right ones are ticked to send by default.
- Confirm the dispensing quantity and ordering prescriber are required when medications are being sent, and that the request arrives in the pharmacy queue.
- Create a prescription with send to pharmacy selected and confirm the prescription type behaves as expected.

**_Lab requests_**

- Enter a result outside its reference range and confirm it is flagged in the lab request view, with the tooltip naming the bound breached.
- Edit a saved result and confirm the edited-entry marker and legend appear.
- If enabling the priority settings, confirm a priority is required at creation and that editing is refused after submission.

**_Vitals and charting_**

- Confirm the new time ranges appear for vitals and charts at the encounter level and for program registry charts.

### General

- Test all bug fixes mentioned in the release notes.
- Verify that existing workflows continue to function as expected.
