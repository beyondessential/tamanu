Tamanu v2.67 release notes

Tamanu v2.67 is a smaller release. Its main change lets staff log in to a new facility server as soon as setup finishes, without waiting for its first sync. It also moves patient record import and export into a 'Patient data' view in the admin panel, adds 'Patient type' to emergency encounters, and shows stock in the 'Send to pharmacy' modal. Custom reports that read the discharge, invoice, outpatient appointment or vaccine change logs need updating, as some of their columns are renamed or change type.

🌟Major Features and Changes

System Administration

Facility server setup

Staff can now log in to a new facility server as soon as setup finishes. Until this release, every login was refused until the server's first sync had downloaded all of the facility's data. That can take hours, and the refusal read as though the user had no access. Now staff are told the facility is being set up, and are taken on to Tamanu once the data has arrived.

Key features

  • Ready to log in after setup - The setup wizard downloads the facility's users, roles, permissions and settings from the central server as part of setup, then logs the installer in. No patient data is downloaded at this stage.
  • 'Setting up this facility' screen - Anyone who logs in before the first sync finishes, whatever their role, sees a screen saying the facility's data is loading for the first time. Once the first sync completes they carry on to facility selection automatically. The screen has a 'Log out' button.
  • Servers set up without the wizard - Facility servers configured another way download the same starter data before their first sync, so they get the same behaviour.
  • First sync unchanged - The first sync still downloads all of the facility's data, taking about as long as before.

🔧System Enhancements

  • Patient data view - Patients and administered vaccines are imported and exported through a new 'Patient data' view in the admin panel, separate from reference data. The spreadsheet format and the test import are as before. Before an import runs, a confirmation explains that it creates new records and overwrites matching patient data, and cannot be undone.
  • Patient type on emergency encounters - The 'New emergency triage' form has a 'Patient type' field, filled in from the patient's details where one is recorded, and price lists set up for a patient type apply to the emergency encounter. Changing it on the form does not change the patient's details. The encounter's details show its patient type, which can be changed through 'Edit encounter details' and carries through when the patient is admitted to hospital.
  • Stock when sending to pharmacy - The 'Send to pharmacy' modal has a 'Stock' column showing whether each medication is in stock at the facility, matching the 'Dispense medication' modal. Hovering over an in-stock medication shows the quantity on hand. Stock is for information only and does not stop a medication being sent.
  • AI settings - The AI model settings suggest the models available to the deployment's Anthropic account, and changes to AI settings take effect without restarting the central server.
  • Longer form logic - Program form questions accept longer visibility criteria and calculations, so complex conditions no longer hit a length limit.
  • Database interruptions - Servers stay up through a brief loss of their database connection, such as a database failover, and carry on once it returns rather than shutting down and restarting. A server only stops if the outage lasts several minutes.
  • Sync history - Facility servers keep a record of every sync attempt and its outcome, so monitoring can pick up a sync that hangs as well as one that fails.

🐛Tweaks and Bug Fixes

Desktop

  • Encounters - Where 'Patient type' is set as required, every encounter form enforces it, including when editing an encounter and admitting to hospital. 'Patient type' is filled in when admitting from triage or from a referral. Editing an emergency encounter refuses an arrival or triage time in the future.
  • Patients - The duplicate NHN check when editing a patient ignores capitalisation. Recording a death with an empty contributing condition row saves without it. A patient removed from a program registry can be registered again.
  • Medications - A medication marked unavailable at the facility shows 'Unavailable' stock rather than 'Unknown'. Users without permission to see the medication administration record or not dispensed details see a message rather than a blank page. Pharmacy note and not dispensed notifications open straight away.
  • Labs and imaging - The active lab requests status filter no longer offers 'Rejected'. Clearing 'Date & time collected' clears the sample details recorded with it. Changing the imaging type clears 'Areas to be imaged'.
  • Invoicing - Saving a procedure no longer overwrites changes the cashier has made to the invoice. An insurance plan, lab test or lab panel with every facility removed from it is offered at all facilities, where before it was offered at none. Clearing an invoice item's quantity no longer causes an error.
  • Vitals and charts - Editing a recorded value no longer fails where the chart includes a question showing the patient's previous answer.
  • Tables - Newly added rows stay selected in selection tables, and removing the last rows on a page no longer leaves an empty page.
  • Admin panel - The reference data 'Manage' tab checks permissions for each data type, applies the same code and id rules as the import, enforces required fields when editing, and saves an optional number field once it is cleared. Drug routes are checked on import. Vaccine consent import and export are tightened, and re-importing an exported administered vaccines sheet keeps the vaccines' encounters and circumstances. Imported dates of birth and vaccine dates are no longer shifted by the server's timezone. Export is unavailable until a data type is selected. The hidden sync button is removed from the central server's admin panel.

Mobile

  • Sync - Saving pulled data during sync is faster.
  • Forms - The village is kept after submitting a program form, and the hardware back button leaves the 'Programs' screen.
  • Patients - A patient with no recorded allergies shows 'None recorded'.

System

  • Sync - Sync no longer fails when a record deleted on the central server has also been updated at a facility. Prescriptions pulled to a facility are no longer pushed straight back, which could keep them syncing between facilities indefinitely. Resolving duplicate patient display IDs ignores capitalisation. Settings that only apply to the central server are kept off facility servers and mobile devices, and removed from them at upgrade.
  • Sensitive networks - AI patient summaries leave out everything recorded in encounters at facilities in a sensitive network, wherever the summary is generated.
  • Integrations - FHIR medication requests carry the dispense quantity in the standard format.

📊Reporting Schema Changes

The change-log base models are made consistent with each other, which renames some of their columns, and new metrics cover prescribing, medication given and antenatal contacts. The encounter summary and invoice products summary reports change what they output, and the immunisation metrics count doses they previously left out. These changes were also released in reporting release v2.66.1, so a deployment already running it has them in place.

Breaking changes

  • Discharge change log - In discharges_change_logs, change_id is renamed changelog_id, changed_datetime is renamed logged_at, and changed_by_user_id is renamed updated_by_user_id.
  • Invoice change log - In invoices_change_logs, change_id is renamed changelog_id. logged_at changes from a timestamp with time zone to a timestamp in the deployment's local time, so comparisons against it shift by the UTC offset.
  • Outpatient appointment change events - In outpatient_appointments_change_events, id is renamed changelog_id and record_id is renamed appointment_id. logged_at and record_updated_at change from UTC timestamps with time zone to timestamps in local time.
  • Vaccine change log - In vaccine_administrations_change_logs, created_at is renamed record_created_at and updated_at is renamed record_updated_at. Their values are unchanged, and ds__vaccinations still outputs updated_at.

New

  • Discharge change events - discharges_change_events is a lighter version of the discharge change log, quicker to filter by discharge or encounter.
  • Medication doses - medication_administration_record_doses holds one row per dose recorded as given.
  • Medication metrics - metric__prescription, metric__prescription_discontinuation (with discontinuing_reason) and metric__medication_administration are added. metric__pharmacy_order gains has_dispense and minutes_to_first_dispense.
  • Antenatal metric - metric__who_dak_anc_indicators counts antenatal contacts under the who_dak_anc_contact metric, with contact_number and gestational_age_weeks.
  • Inpatient separations - metric__inpatient_admission adds an inpatient_separation metric, one row per closed admission dated at discharge, with patient_days and is_same_day filled on those rows.
  • Immunisation metrics - metric__immunisation_dose and metric__immunisation_refusal gain person_id, vaccine_id, vaccine_label, vaccine_category, location_group_id, age_days, age_years, facility_source and is_given_elsewhere.
  • Lab and birth metrics - metric__lab_order gains request_status, cancellation_reason, location_group_name and turnaround__minutes. metric__birth gains patient_location_id, the newborn's village.
  • Other columns - encounter_diets gains created_datetime and ds__invoice_products gains available_facility_ids. The patient, patient additional data, program registration, invoice, discharge and vaccine change logs and the outpatient appointment change events gain logged_at_utc, and the program registration, vaccine and appointment ones also gain record_updated_at_utc, for ordering history across a daylight saving change.

Changed

  • Encounter summary reports - In the standard and sensitive reports, by start and by end date, vaccinations list only vaccines that were given, and an encounter with several triages gives one row for its earliest triage, so row counts can fall. The encounter type parameter offers Outpatient, Emergency and Inpatient, and an emergency encounter later admitted appears under both Emergency and Inpatient.
  • Invoice products summary - The report takes a facility parameter. With a facility set, it lists only products available there, and leaves the price columns blank for price lists that don't apply to it.
  • Immunisation metrics - Doses and refusals with no location of their own take the encounter's location, and doses given elsewhere are kept, so counts rise.
  • Inpatient admission metric - Admission rows are unchanged, but the separation rows roughly double the model, so a query summing value_numeric without filtering on metric_id over-counts.
  • Encounter diets line list - The report no longer fails for a patient in an open encounter aged between 8 days and 1 month.

⚠️Critical Upgrade Notes

Required

Patient type

  • Where your deployment sets 'Patient type' as required, staff must now choose one on every encounter form, including emergency triage, admitting to hospital and editing an encounter. Until now some of these forms saved without one.
  • Check that the patient type list is complete, and let triage and admissions staff know.

Patient data

  • Patients and administered vaccines are imported and exported only through the new 'Patient data' view, not the reference data view. Let anyone who imports or exports patient records know where to find them.

Reports

  • Some columns in the discharge, invoice, outpatient appointment and vaccine change logs are renamed, and some times in the invoice and appointment change logs now hold local time. Custom reports that use them will fail or show shifted times after upgrade. Update them using the reporting schema changes above.
  • Immunisation dose and refusal figures rise, as doses with no location of their own and doses given elsewhere are now counted. Encounter summary reports list only given vaccines and one triage per encounter. Let anyone who tracks these figures know.
Optional

Facility server setup

  • When setting up a new facility, let its staff know they will see a setting-up screen until the first sync finishes, and that they can log in during that time.

AI settings

  • Where AI features are in use, review the selected models against the suggestions now offered in the AI settings.

Upgrade Steps and Recommended Testing

Required

Patient type

  • On a deployment where 'Patient type' is required, create an emergency encounter for a patient with a patient type recorded. Confirm the field is filled in and cannot be left empty, then admit the patient to hospital and confirm the patient type carries over.

Patient data

  • Run a test import of a patient spreadsheet in the 'Patient data' view, and export patients and administered vaccines from it.

Reports

  • Run any custom reports that read the discharge, invoice, outpatient appointment or vaccine change logs, and confirm they complete.
Optional

Facility server setup

  • When next setting up a facility server, confirm you can log in straight after the setup wizard, see the setting-up screen, and reach facility selection once the first sync completes.

General

  • Upgrade an existing Tamanu Mobile device, record some data and sync. Confirm the sync completes and the new records appear on Tamanu Desktop.
