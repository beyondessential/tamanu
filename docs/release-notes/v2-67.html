Tamanu v2.67 release notes

Tamanu v2.67 is a smaller release. Its main change lets staff log in to a new facility server as soon as setup finishes, without waiting for its first sync. It also moves patient record import and export into a 'Patient data' view in the admin panel, adds 'Patient type' to emergency encounters, and shows stock in the 'Send to pharmacy' modal.

🌟Major Features and Changes

System Administration

Facility server setup

Staff can now log in to a new facility server as soon as setup finishes. Until this release, every login was refused until the server's first sync had downloaded all of the facility's data. That can take hours, and the refusal read as though the user had no access. Now staff are told the facility is being set up, and are taken on to Tamanu once the data has arrived.

Key features

  • Ready to log in after setup - The setup wizard downloads the facility's users, roles, permissions and settings from the central server as part of setup, then logs the installer in. No patient data is downloaded at this stage.
  • 'Setting up this facility' screen - Anyone who logs in before the first sync finishes, whatever their role, sees a screen saying the facility's data is loading for the first time. Once the first sync completes they carry on to facility selection automatically. The screen has a 'Log out' button.
  • Servers set up without the wizard - Facility servers configured another way download the same starter data before their first sync, so they get the same behaviour.
  • First sync unchanged - The first sync still downloads all of the facility's data, taking about as long as before.

🔧System Enhancements

  • Patient data view - Patients and administered vaccines are imported and exported through a new 'Patient data' view in the admin panel, separate from reference data. The spreadsheet format and the test import are as before. Before an import runs, a confirmation explains that it creates new records and overwrites matching patient data, and cannot be undone.
  • Patient type on emergency encounters - The 'New emergency triage' form has a 'Patient type' field, filled in from the patient's details where one is recorded. Changing it on the form does not change the patient's details. The patient type carries through when the patient is admitted to hospital.
  • Stock when sending to pharmacy - The 'Send to pharmacy' modal has a 'Stock' column showing whether each medication is in stock at the facility, matching the 'Dispense medication' modal. Hovering over an in-stock medication shows the quantity on hand. Stock is for information only and does not stop a medication being sent.
  • AI settings - The AI model settings suggest the models available to the deployment's Anthropic account, and changes to AI settings take effect without restarting the central server.
  • Longer form logic - Program form questions accept longer visibility criteria and calculations, so complex conditions no longer hit a length limit.
  • Database interruptions - Servers stay up through a brief loss of their database connection, such as a database failover, and carry on once it returns rather than shutting down and restarting. A server only stops if the outage lasts several minutes.
  • Sync history - Facility servers keep a record of every sync attempt and its outcome, so monitoring can pick up a sync that hangs as well as one that fails.

🐛Tweaks and Bug Fixes

Desktop

  • Encounters - Where 'Patient type' is set as required, every encounter form enforces it, including when editing an encounter and admitting to hospital. 'Patient type' is filled in when admitting from triage or from a referral. Editing an emergency encounter refuses an arrival or triage time in the future.
  • Patients - The duplicate NHN check when editing a patient ignores capitalisation. Recording a death with an empty contributing condition row saves without it. A patient removed from a program registry can be registered again.
  • Medications - A medication marked unavailable at the facility shows 'Unavailable' stock rather than 'Unknown'. Users without permission to see the medication administration record or not dispensed details see a message rather than a blank page.
  • Labs and imaging - The active lab requests status filter no longer offers 'Rejected'. Changing the imaging type clears 'Areas to be imaged'.
  • Invoicing - Saving a procedure no longer overwrites changes the cashier has made to the invoice. An insurance plan, lab test or lab panel with every facility removed from it is offered at all facilities, where before it was offered at none.
  • Tables - Newly added rows stay selected in selection tables, and removing the last rows on a page no longer leaves an empty page.
  • Admin panel - The reference data 'Manage' tab checks permissions for each data type, applies the same code and id rules as the import, and enforces required fields when editing. Drug routes are checked on import. Vaccine consent import and export are tightened, and re-importing administered vaccines keeps their existing encounters. Export is unavailable until a data type is selected. The hidden sync button is removed from the central server's admin panel.
  • Forms - Signature questions save and display correctly.

Mobile

  • Sync - Saving pulled data during sync is faster.
  • Forms - Multi-select answers display correctly, the village is kept after submitting a program form, and the hardware back button leaves the 'Programs' screen.
  • Patients - A patient with no recorded allergies shows 'None recorded'.

System

  • Sync - Sync no longer fails when a record deleted on the central server has also been updated at a facility. Resolving duplicate patient display IDs ignores capitalisation. Settings that only apply to the central server are kept off facility servers and mobile devices, and removed from them at upgrade.
  • Sensitive networks - AI patient summaries leave out everything recorded in encounters at facilities in a sensitive network, wherever the summary is generated. Editing a facility in the reference data admin cannot change its network.
  • Integrations - FHIR medication requests carry the dispense quantity in the standard format.

⚠️Critical Upgrade Notes

Required

Patient type

  • Where your deployment sets 'Patient type' as required, staff must now choose one on every encounter form, including emergency triage, admitting to hospital and editing an encounter. Until now some of these forms saved without one.
  • Check that the patient type list is complete, and let triage and admissions staff know.

Patient data

  • Patients and administered vaccines are imported and exported only through the new 'Patient data' view, not the reference data view. Let anyone who imports or exports patient records know where to find them.
Optional

Facility server setup

  • When setting up a new facility, let its staff know they will see a setting-up screen until the first sync finishes, and that they can log in during that time.

AI settings

  • Where AI features are in use, review the selected models against the suggestions now offered in the AI settings.

Upgrade Steps and Recommended Testing

Required

Patient type

  • On a deployment where 'Patient type' is required, create an emergency encounter for a patient with a patient type recorded. Confirm the field is filled in and cannot be left empty, then admit the patient to hospital and confirm the patient type carries over.

Patient data

  • Run a test import of a patient spreadsheet in the 'Patient data' view, and export patients and administered vaccines from it.
Optional

Facility server setup

  • When next setting up a facility server, confirm you can log in straight after the setup wizard, see the setting-up screen, and reach facility selection once the first sync completes.

General

  • Upgrade an existing Tamanu Mobile device, record some data and sync. Confirm the sync completes and the new records appear on Tamanu Desktop.
